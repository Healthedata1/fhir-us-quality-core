
# CLAUDE.md

## Repository purpose
This repo is a working area for review of the US Quality Core Implementation Guide
1.0.0-ballot - STU 1 - ballot.

This is published as a github page to share
during development so supports a full ig-publication stack but is not formally published
as an HL7 guide.



This build uses `/Users/ehaas/Documents/FHIR/Healthedata1-Sandbox/publish.sh` and is run in two steps as a bash alias
  1. `pig -s` — run SUSHI
  2. `pig -iq` — run the IG Publisher and view the QA report/differential

The IG Publisher JAR location is configured via the `ig_path` variable on line 44 of publish.sh (defaults to `$HOME/Downloads/org.hl7.fhir.igpublisher.jar`).
After a successful build, the IG publisher generates a detailed QA page at `output/qa-eslintcompact.txt` — it is NOT committed to git
- `.qa-eslintcompact_previous.txt` is a local baseline copy saved before each build, also NOT committed
- When asked about QA, sort and compare these two files and only list new and resolved issues


## FHIR version
- FHIR R4 (4.0.1)
- US Core baseline: version 9 ( current)
- USCDI+ Quality: draft V2, published July 2026 (built on USCDI v6)


### Key Directories

| Directory | Purpose |
|-----------|---------|
| `input/fsh/` | .fsh source files for conformance (extensions, profiles, valuesets, search-parameters) and example resources |
| `input/pages/` | Markdown narrative pages (index.md, conformance.md, guidance.md, etc.) |
| `input/intro-notes/` | Per-artifact intro/notes markdown fragments (144 files) |
| `input/includes/` | Reusable Jekyll include fragments |
| `input/data/` | data collections used to generate the resources and narratives |
| `input/images/` | Images |
| `input/images/generated` | data source unclear if used anymore |
| `fsh-generated/` | SUSHI output: all generated conformance resources and examples (218 files in the last build), including the generated ImplementationGuide resource |
| `output/` | Built IG (HTML, JSON, XML, packages) — gitignored |
| `scripts/` | javascript files for generating the ig resources and narrative content|


### Configuration Files

- **`sushi-config.yaml`** — Main IG configuration (version, dependencies, page hierarchy, parameters). SUSHI only generates the ImplementationGuide resource from this (see next item); it does NOT author FHIR artifacts.
- **`ImplementationGuide-hl7.fhir.us.quality-core.json`** - ImplementationGuide resource generated from sushi-config.yaml; in addition to the sushi-config.yaml content, it adds the resources section listing all the IG conformance resources and examples
- **`ig.ini`** — Points IG Publisher to the generated ImplementationGuide resource and specifies the HL7 template version.
- **`publication-request.json`** — HL7 publication metadata (updated before each publication).

### QA Files
- **`output/qa-eslintcompact.txt`** — QA report generated after running the build
- **`input/ignoreWarnings.txt`** — QA report warning suppressions.

### LLM friendly files:
This is an "LLM-ready" view of the IG pages in Markdown format created as the build output from the static HTML pages. This format reduces the IG size and is designed to help an LLM handle the IG contents more easily.

- **llms.txt**: An llms.txt manifest — a machine-readable index of the IG's Markdown files.
- **ai.zip**: Markdown version of each HTML page bundled in a zip file.

## Naming Conventions

- Profiles: `StructureDefinition-us-quality-core-[resource].json`
- Extensions: `StructureDefinition-us-quality-core-[name].json`
- Search Parameters: `SearchParameter-us-quality-core-[resource]-[param].json`
- Intro/Notes files: `StructureDefinition-us-quality-core-[resource]-intro.md` / `-notes.md`

## Authoring conventions

## Jekyll/Liquid Templating

Pages use Jekyll with Liquid templating:
- **Include files** (`input/includes/`): Reusable fragments inserted via `{% include filename.md %}`. Include files with parameters document their parameters in inline comments at the top.


## USCDI alignment
Each profile maps to one or more USCDI+ Quality V2 Data Elements.
USCDI+ Quality data Class and descriptions are in `input/data/` json files and possibly the csv files.


## What Claude should and shouldn't touch
- OK to edit: files in `input/fsh`, `input/pages`, `input/includes`, `input/intro-notes`, `ONC Docs`, `input/ignoreWarnings.txt`, `sushi-config.yaml`
- OK to read for reference: `output/`, `temp/`, `template/`
- Do not edit: `input/data/`, `input/images/`, `output/`, `temp/`, `template/`, `fsh-generated/` (these are generated files)
- Do not invent: bindings, mustSupport flags, USCDI mappings, extensions or history not present in the source SD. If a fact is needed and not
  in the file, ask rather than fabricate.

## House style for prose (READMEs, descriptions, commit messages)
- Present tense, third person. No "we," "you."
- RFC 2119 keywords (SHALL/SHOULD/MAY) used in the normative sense only.
  - Use "might" or "can" instead of "MAY"
- No marketing adjectives: "robust," "comprehensive," "seamless."
- No hedges: "typically," "generally," "may currently."
- Plain ASCII; straight quotes; no em dashes.
- Spell out acronyms on first use except FHIR, US Core, USCDI, HL7, SNOMED CT, LOINC.
